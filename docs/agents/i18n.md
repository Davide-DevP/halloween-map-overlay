# Translation

[← AGENTS.md](../../AGENTS.md) · **Read before** touching `src/shared/i18n.js`, `src/js/i18n.js`,
`src/core/language.js`, `src/i18n/*.json`, `updater/strings.json` or any
user-visible string anywhere.

`src/shared/i18n.js` is the whole mechanism: six flat JSON catalogues, dotted
keys, `{param}` placeholders, no framework. Setting `language` = `system`
(default), `en`, `it`, `es`, `de`, `fr`, `pt-BR`.

- **Everything user-facing goes through it.** The test
  `test/i18n.test.js` scans the source for keys and fails on a key with no
  translation, on a catalogue string nothing uses, on a key set (or key
  *order*) that differs between catalogues, on a `{param}` one language
  dropped, on an HTML tag one language dropped, on a string still identical to
  English, on a `<label>`/`<button>`/`<option>`/`<th>`/`<hN>` in
  `src/index.html` with no `data-i18n`, and on an English **fallback** in
  `src/index.html` that no longer matches `en.json`. Nothing in the test names
  a key — the source *is* the list.
- **Fallback chain**: the requested language → English → the key itself, so a
  missing string shows English and never blanks an element. A `{param}` with
  nothing supplied is **left in the string**: electron-updater's notification
  body carries its own `{appName}`/`{version}` and substitutes them after we
  have translated it.
- **Two arities of `t()`.** `src/shared/i18n.js` is pure and takes the language
  (`t(lang, key, params)`); `src/js/i18n.js` is a module-level singleton for the
  window, so a view module writes `t('nav.settings')`. One value per window, one
  place a language change has to reach.
- **Not translated, on purpose**: map names, creator names, the product name
  ("Halloween Map Overlay" in the title bar, the nav brand, the preview canvas),
  the OBS window title (renaming it would break users' existing OBS sources),
  OS-supplied display names, and the language names in the picker (marked
  `data-i18n-ignore`, which is also how the test is told an element is exempt).
  The full list, and the in-game terms that stay English, is below.
- **Static markup**: `data-i18n` (text), `data-i18n-html` (strings containing
  `<kbd>`/`<strong>`/`<a>` — the FAQ and the longer help paragraphs),
  `data-i18n-title`, `data-i18n-placeholder`, `data-i18n-aria-label`. The `-html`
  form only ever inserts our own catalogue strings; everything else still goes
  through `escapeHtml`.
- **The English inside the markup is a fallback, and it is tested.**
  `applyDom()` overwrites it on the first pass, so nobody running the app ever
  sees it — which is exactly why it rots. It was 35 elements out of date
  before the test existed: a button reading *Check for new maps* whose
  catalogue string is *Check for new maps now*, a help text still claiming the
  update check was "the only network request this app makes", most of the FAQ
  cut to its first sentence. Change a string in `en.json` and change the
  fallback in the same commit.
- **Main never sends English.** `sendUpdate('…')` is `sendUpdate(msg('key'))`
  and the renderer translates on arrival (`translateMessage`), so a toast that
  is already on screen when the language changes is not stranded. The same for
  the `{ok, message}` an IPC handler returns to the hotkey toast. The exceptions
  are the two things **main draws itself** — the tray menu and the
  "already running" dialog — which use `Language.t()` / `t(lang, …)`.
  The toast is rendered with `.text()`, so a catalogue string that reaches it
  names a button **in quotes**, never in `<em>` (`update.downloaded`).
- **A parameter can itself be a message.** `"X is already bound to <action>"` is
  one sentence with a translatable noun inside it, and main does not know the
  window's language, so the inner half travels as `{key}` too and `t()` resolves
  it in the same pass. See `conflictMessage` in `src/core/hotkeys.js`.
- **`SYSTEM_HOTKEY_DEFS` carries both** `description` (English, the fallback and
  the documentation) and `descriptionKey`. A test asserts they agree, so the
  two cannot drift.
- **Dynamic content must re-render.** `i18n.onChange(cb)` in the renderer: the
  gallery, both hotkey tables, the custom list, the detector status line, the
  monitor picker, the update banner and the cached preview canvas all register
  one. Anything built with `t()` at render time and *not* registered keeps the
  old language until something else touches it. `setLanguage()` ignores a repeat
  of the language already applied, because a switch reaches the renderer
  **twice** — once from the select's own handler and once from main's
  `language-changed` push (the push is what also rebuilds the tray).
- **The overlay and the OBS window get `language-changed` too.** The marker
  **legend** is the only translated thing on either of them, and it is
  re-labelled in place from the last `map-change` payload rather than waiting
  for main to re-send the map.
- **Resolution happens in main**, once (`src/core/language.js`, `app.getLocale()`
  → `systemLanguage()`). The renderer asks with `get-language`, writes
  with `set-language`, and main pushes `language-changed` to the window and
  rebuilds the tray from the same callback. The second-instance branch in
  `index.js` has no `Settings`, so it uses
  `Language.languageWithoutSettings()`, which reads the file directly rather
  than registering a second set of IPC handlers in a process that is quitting.
- `DEBUG=true` logs `i18n::applyDom <lang> elements=N` — a DOM that was not
  translated otherwise looks exactly like a DOM that happens to be English.

`LANGUAGES` in `src/shared/i18n.js` is the list and its first entry, `en`, is

## Adding a language

Six things, and a test fails for each one you forget (for the sixth,
`test/packaging.test.js` only checks that the language is covered at all — the
regional variants are on you):

1. `src/i18n/<code>.json` — exactly `en.json`'s keys, in `en.json`'s **order**,
   with `en.json`'s blank-line grouping and 2-space indent, UTF-8 without a
   BOM, **CRLF line endings** (that is what the existing files use).
2. `require` it in `src/shared/i18n.js` and add the code to `LANGUAGES` and
   `CATALOGUES`.
3. One `<option value="<code>" data-i18n-ignore>Name</option>` in the
   `#languageSelect` of `src/index.html`. The setup tutorial borrows that very
   `<select>` (`<template data-borrow="languageSelect">`), so there is nothing
   to add there.
4. A rule in `SYSTEM_LANGUAGE_RULES` if an OS locale should pick it.
5. The README "Language" section (in English).
6. **The Chromium locale in `package.json` `build.electronLanguages`.** Since
   the 0.7.x installer trim the app ships only the `locales/*.pak` files listed
   there (en-US, it, es, es-419, de, fr, pt-BR, pt-PT — about 35 MB less
   installed than Electron's full set). `app.getLocale()` reports the locale
   Chromium actually *loaded*, so a system language whose `.pak` is missing
   falls back to `en-US` and `SYSTEM_LANGUAGE_RULES` never sees it: the new
   language would work when picked by hand and silently not as "System". Add
   every regional variant an OS may report (that is why `es-419` and `pt-PT`
   are there).

**The catalogue itself needs no packaging change.** `package.json` `build.files`
is a list of exclusions only, so everything under `src/` — including a new
`src/i18n/*.json` — is packaged automatically. Nothing else is locale-dependent either: there is
no `Intl` or `toLocaleString` call in the app, and `detector.detectedAt`'s
`{time}` is hand-formatted 24 h `HH:MM`. `<html lang>` is set at runtime by
`applyDom()` in `src/js/i18n.js` from the resolved language code, so `pt-BR`
lands there as a valid BCP 47 tag with no extra work.

## The system-language rule

`systemLanguage(locale)` in `src/shared/i18n.js` — pure, exported on its own
and unit-tested case by case in `test/i18n.test.js` (`SYSTEM_LOCALE_CASES`).
`resolveLanguage(setting, locale)` is just "an explicit choice, else this".

```
it*  → it      es*  → es      de*  → de
fr*  → fr      pt*  → pt-BR   everything else → en
```

Three details that are decisions, not accidents:

- **The match is on the primary subtag, not a prefix of the string.** Each rule
  is `/^xx\b/i`, so `it-IT`, `it_IT` (underscores are folded first) and `IT-it`
  are Italian while `italian`, `esperanto`, `deutsch`, `french` and
  `portuguese` are all English. That `\b` was already load-bearing for `it`;
  adding `es`, `de`, `fr` and `pt` makes it carry four more near-misses.
- **Every `pt*` locale gets Brazilian Portuguese**, `pt-PT` included. There is
  one Portuguese catalogue; a European Portuguese reader is served far better
  by it than by English. If a `pt-PT` catalogue is ever added, this is the one
  rule that has to become two.
- **`pt` is not a setting value.** The stored setting is `pt-BR`; `pt` only
  exists as a locale prefix. `resolveLanguage('pt', 'de-DE')` is therefore
  `de` — the setting is unrecognised, so the locale wins.

## Not translated, and why

On top of the rule above (map names, creator names, the product name, the OBS
window title, OS-supplied display names, the picker's language names):

- ***Halloween: The Game*** — the game's own title.
- **"Borderless Windowed"** — the label in the game's video settings. The
  player has to find that exact string on their own screen, so it is kept in
  English in all six languages, with a short native gloss in brackets the first
  time it appears in a paragraph (`(finestra senza bordi)`, `(ventana sin bordes)`,
  `(randloses Fenster)`, `(fenêtre sans bordure)`, `(janela sem bordas)`). **The game has no
  exclusive-fullscreen mode**; no catalogue string may claim it does, and the
  reason the overlay needs a windowed game is that the overlay is itself an
  always-on-top *window*. A game window **with** a border or title bar is a
  second, separate problem: it makes Tab-map mode refuse to draw
  (`TabMode.noteRect` → `sizeMismatch`), which
  `settings.tabMarkers.method.windowed` explains.
- **`Ctrl`, `Alt`, `Shift`, `Super`, `Tab`** — **key caps are produced by code,
  not by the catalogue.** `acceleratorToDisplay()` in
  `src/shared/hotkeys-constants.js` renders every accelerator as
  `Ctrl + Alt + R` regardless of language, and `vkLabel()` in
  `src/shared/key-codes.js` names the map key (`Tab`, `M`, `F1`, …). The
  `<kbd>` chips in the Hotkeys table, the setup tutorial and the FAQ all come
  from there. Prose that spells a key therefore uses the **same tokens the
  chips do**, in every language: writing "Strg" or "Maj" in a sentence next to
  a `<kbd>Ctrl</kbd>` would be a second, contradictory naming system.
  The local key cap is glossed **once**, in `hotkeys.error.noModifier`, where a
  user who just pressed the wrong thing is looking:
  `Ctrl/Strg` (de), `Shift/Maj` (fr), `Shift/Mayús` (es). PT-BR keyboards use
  Ctrl/Alt/Shift, so there is no gloss.
  *If accelerators are ever localised, that has to happen in
  `acceleratorToDisplay`, not in the catalogues.*
- **`Custom`** — the reserved creator name for imported images, a catalogue key
  on disk, not a word.
- Product and proper nouns: `OBS`, `GitHub`, `GitHub Releases`, `Discord`,
  `NVIDIA`, `Windows`, `Wayland`, `Apache`, `DBD Map Overlay`, `LucaFontanot`,
  `u/deftyconchgaming`, `r/TheHalloweenGame`, `detector.log`,
  `npm run prepare-maps`, `%LOCALAPPDATA%\Programs\Halloween Map Overlay`,
  `PNG`/`JPG`/`WEBP`, `HTTPS`.
- **Windows' own UI path in `faq.updates.a2` *is* translated**, to the names
  Windows actually shows in that language — the point of the sentence is that
  the reader can find the screen. Italian already did this.

The game is treated as **not localised into any of these languages** (it cannot
be checked from here), which is why in-game UI terms stay English with a gloss
rather than being translated outright.

## One word, one meaning

Two English words used to mean two things each, and both were mistranslated
before the wording was fixed. Keep them apart:

- **"held"** is now only a key physically held **down** (`faq.keyboard.a`). A
  combination the app has taken from Windows is **taken** or **reserved**
  (`hotkeys.gameOnly.help`, `hotkeys.error.takenByOther`,
  `onboarding.hotkeys.tryIt.taken`). Privacy text sits next to both, so one
  word may not carry both meanings.
- **A label quoted inside another string** is spelled **exactly** like the
  control it names, in every language: `<em>Recognise the map automatically</em>`
  and `<em>On the game's map</em>` in `faq.reads.a`, `faq.screenshots.a`,
  `faq.keyboard.a` and `faq.autodetect.a`; `hotkeys.help` quotes the Edit
  button and therefore has to say whatever `common.edit` says; `update.ready.body`
  and `update.downloaded` quote `update.restart`. When a control is relabelled,
  grep for every string that quotes it before finishing — the 1.0 copy pass had
  to go through those four FAQ answers twice.
- `hotkeys.modal.listening` says **"Waiting for keys…"**, not "Listening…", in
  an app whose FAQ insists it does not listen to the keyboard.
- `settings.tabMarkers.mapKey.change` is the key button's **idle** label
  ("Change key…"); `…mapKey.press` is the armed one ("Waiting for a key…").
  `Options.renderMapKey()` sets the first, the click handler the second — do
  not swap them.

(`Usa…` reads as an order), so `settings.tabMarkers.method.*` names the app:
*La app usa el método más lento…*.

*Storm cellar* and *Cellars*, so Portuguese names the place, not the door.

`hotkeys.col.hotkey` is *Tecla*, like `hotkeys.col.binding`: it was still
*Atalho* after the 1.0 copy pass, which is exactly the "atalho where the table
meant one key" the glossary above forbids — the column shows one key.

Verbs split by what is being touched: a key is **apertada** and a button gets
**clique em**. That keeps *reservar* for the one promise that the app does
**not** reserve the map key, and leaves *em uso* for a combination another
program owns. Portuguese also avoids the bare 3rd-person verb at the head of a
help line, so `settings.tabMarkers.method.*` starts with the gerund
(*Usando o método mais lento…*), which reads as a report and not as an order.

Informal **tu** throughout (see *Register* below), short sentences, and the word
a French player actually says. Before the 1.0 copy pass the catalogue said
*overlay* on nine screens, *marqueurs* next to *points*, *Combinaison* where the
table meant one key, *détecter* where English meant *recognise*, and
*Chercher les nouveautés tout seul* where English meant updates. One term per
concept:

| Concept | The word | Never |
|---|---|---|
| the app's own key combinations | **les raccourcis** | hotkeys, touches rapides, combinaisons |
| one action's combination | **la touche** (« Enlever la touche », « aucune touche ») | combinaison, attribuer / libérer, non attribué |
| the markers, in anything a player reads | **les points** | marqueurs |
| the window in the corner | **la carte**, **la carte dans le coin** | overlay |
| the map the game itself draws | **la carte du jeu** | carte en jeu, carte in-game |
| what auto-detect does | **reconnaître la carte** | détecter, détection automatique |
| the first-run tour | **le guide de démarrage** | tutoriel, assistant |
| the tray | **près de l'horloge** | zone de notification, barre des tâches, tray |
| the opacity sliders | **Visibilité**, **Visibilité des points** | opacité, transparence, « à quel point on la voit » |
| the sample map Settings puts on screen | **une carte de test** | aperçu, carte d'exemple |
| the section over the main hotkey table | **Touches principales** | Système |
| the log files, to a player | **ces fichiers** (« Ouvrir le dossier de ces fichiers ») | journaux, logs, dossier des journaux |
| the points flashing | **clignoter** | scintiller, papilloter |
| a combination another program owns | **un autre programme l'utilise déjà** | réservé, pris |
| pressing a key / clicking a button | **appuyer sur** / **cliquer sur** | presser, enfoncer (except "held down") |

The chips and the legend share their noun, as in Italian, Spanish and German:
`markers.chip.cellar` is *Caves* and `markers.layer.cellar`
*Cave — position possible*; *Portails* / *Portail de sortie* and *Essence* /
*Jerrican d'essence* work the same way. French names the **place**, like English
*Storm cellar* / *Cellars*, and not the hatch Italian and German point at
(*botola*, *Luke*) — if the hatch word is ever wanted in every language, French
is *Trappe* / *Trappes*. `overlay.previewWatermark` is *ESSAI* rather than
*TEST*, which would be identical to English, and `overlay.sampleMap` is
*Carte de test*, the one word the two preview notices use as well.

`hotkeys.col.action` is the single French string still identical to English, and
`MAY_MATCH_ENGLISH` in `test/i18n.test.js` keeps it exempt for that reason.
`hotkeys.col.hotkey` is *Touche*, like `hotkeys.col.binding`, because each row
shows one key. `settings.value.px` / `settings.value.percent` carry the no-break
space, so they are not byte-identical to English even though the same whitelist
would have allowed it.

Four French specifics:

- **A help line may not start with a bare verb.** *Utilise ta touche de carte…*
  is spelled exactly like the `tu` imperative and reads as an order, so
  `settings.tabMarkers.method.*` names the app as its subject
  (*L'app utilise…*) — the same trap the Italian, Spanish, Portuguese and German
  help lines have.
- **The strings that quote an accelerator dodge gender.** `{accelerator}` and
  `{key}` stand for a token whose gender no sentence can know, so
  `hotkeys.error.*` is written around it: *« … » sert déjà à …*,
  *Un autre programme utilise déjà « … »*, *Impossible d'utiliser « … »*,
  *… fait aussi partie des touches principales*. Never *« … » est déjà
  attribué(e)*.
- **`settings.hardwareAcceleration` says *pour l'affichage***, not *pour
  dessiner la carte*: *carte graphique* and *la carte* in one label read as the
  same noun twice.
- **The local key cap is glossed once**, `Shift/Maj` in
  `hotkeys.error.noModifier`; every other mention uses the same `Ctrl`, `Alt`,
  `Shift`, `Tab` tokens the `<kbd>` chips are built from.

**Register.** German `du`. Spanish `tú`, neutral international (no *vosotros*,
no regionalisms; `mouse` and `equipo`, not `ratón` and `ordenador`). Brazilian
Portuguese `você`, worded so a European Portuguese reader is not thrown (that
locale gets this catalogue). French **`tu`** — the original brief's default was
*vous*, but the instruction was to match Italian, and the Italian catalogue is
thoroughly informal (`premi`, `puoi`, `il tuo PC`). **Confirmed by the French
review:** `tu` is what Discord and most community gaming tools use in French,
it matches it/es/de, and the file is 100 % `tu` (imperatives included). French
descriptive help texts avoid a bare 3rd-person verb at the start of a sentence
(`Enregistre…`, `Utilise…`), because it is spelled exactly like the `tu`
imperative and reads as an instruction; the same trap exists in Italian and
Spanish (`Usa…`), which is why `settings.tabMarkers.pollingOnly.help` names
the app as the subject in both.

**French typography.** The space before `: ; ? ! %`, inside `« »` and between a
number and its unit is a no-break space, written in `fr.json` as the JSON
escape ` ` (never `&nbsp;`, which would break the entity-parity test and
would show literally in `textContent` strings; never a literal U+00A0, which
is invisible in an editor and easy to lose). Apostrophes stay straight, as in
every other catalogue. The 1.0 copy pass had to put all 124 of them back twice:
a rewrite of `fr.json` turns every escape into a literal U+00A0 unless the
writer puts them back by hand, because `JSON.stringify` emits the byte —
**anything that re-serialises a catalogue has to re-escape U+00A0 on the way
out.** `JSON.parse` cannot tell the two spellings apart, so the only way to see
it is to count the raw bytes (`\xc2\xa0`); *no catalogue holds a literal
no-break space* in `test/i18n.test.js` now does exactly that, for all six files,
and also asserts French still has its ~125 escapes so the test cannot be
satisfied by dropping the spaces instead.

**Punctuation.** `&mdash;` / `&ndash;` are treated as *content*: a language may
use a colon or a comma instead (Italian does in `faq.keyboard.a` and
`faq.updates.a`; German prefers `&ndash;` and `„…“` throughout; Spanish often
uses `:`). `&rarr;` and `&nbsp;` are *structure* and are compared one for one
by the test, as is `&amp;` where it is part of a Windows screen name. Spanish
uses `¿`/`¡`; decimal separators follow the locale (`0,7 s`).

## What the tests check

`test/i18n.test.js`, for **every** catalogue against `en.json`:

- the same key set **in the same key order** (captured at load time — the
  fallback test mutates the Italian object's insertion order);
- no empty or whitespace-only string;
- `{placeholder}` parity per key;
- HTML **tag-name** parity per key (multiset of `em`/`strong`/`kbd`/`code`/`a`,
  opening and closing), plus entity parity for the structural entities;
- the one `<a href>` in `credits.basedOn` is byte-identical everywhere (it is a
  licence obligation, see `NOTICE`);
- nothing identical to English, except an explicit 8-key whitelist
  (`MAY_MATCH_ENGLISH`) — and a second test fails if a whitelist entry stops
  being needed, so the exemption cannot outlive its reason;
- BOM, line endings, indentation and blank-line grouping match `en.json`;
- `#languageSelect`'s options are exactly `LANGUAGE_SETTING_VALUES`, in order,
  and every language name carries `data-i18n-ignore`;
- the set of `src/i18n/*.json` files is exactly `LANGUAGES` — a catalogue
  nobody wired up fails too;
- every English **fallback** in `src/index.html` still equals its `en.json`
  string, entities decoded and whitespace collapsed. Not covered there:
  markup a view module builds with `t()` at render time (it has no attribute
  and so no fallback), `data-i18n-ignore` elements, and an attribute form with
  no literal value beside it;
- **no catalogue file holds a literal U+00A0** — French keeps its ~125
  no-break spaces as `\u00a0` escapes, and the test also asserts they are still
  there, so it cannot be satisfied by deleting them (see *French typography*);
- `systemLanguage()` case by case, including the near-miss words.

`test/onboarding-rules.test.js` and `test/update-message.test.js` iterate
`LANGUAGES`, so a new language is covered by them for free.

## The updater helper's own strings

`hmo-updater.exe` carries its own **en/it** table (`updater/strings.json`,
generated into C# at build time); `test/updater-strings.test.js` asserts it
matches the app's wording and has its own hard-coded `['en', 'it']`. The helper
is deliberately **not** part of the six-language set: it is on screen for a few
seconds during an install. See
[updater-and-installer.md](updater-and-installer.md).

## Keys a reviewer should look at first

Places where the English needed a decision, or still carries one:

- **The long answers come in two `<p>`s**, `faq.X.a` + `faq.X.a2`, and the
  split is by *subject*, not by length: `faq.reads.a2` is the "Technically: …"
  sentence, `faq.screenshots.a2` the `hotkeysGameOnly` foreground poll (which
  captures nothing and so is not an answer to "does it take screenshots"), and
  `faq.keyboard.a2` the app's own hotkeys. Each half has to carry English's
  markup on its own — the tag- and entity-parity tests run per key — so a
  language may not move a `<em>` across the seam. `faq.updates.a`/`.a2` is the
  pattern they follow.
- **`onboarding.hotkeys.maps` takes `{keys}`** and is rendered from
  `src/js/onboarding.js`, like `onboarding.hotkeys.tryIt` and the two FAQ
  answers that name accelerators: the map keys live in `hotkeys.json` and are
  the user's to change, so "each map has its own number" was only ever true of a
  fresh install. With none bound the step uses `onboarding.hotkeys.maps.none`,
  which takes no parameter — never a sentence with an empty gap in it.
- **Every privacy sentence** is translated conservatively and literally, with
  nothing softened and nothing strengthened: `faq.reads.a`,
  `faq.screenshots.a`, `faq.keyboard.a`, `faq.internet.a`,
  `diagnostics.create.help`, `onboarding.done.updates.help`,
  `settings.tabMarkers.method.waiting` and `tabMarkers.fallback`. "Nothing is
  saved and nothing is sent", "no keyboard hook", "it does not reserve the key",
  "no key is read at all" and the one-time capability check must all survive in
  the same scope. These are the first strings to re-read after any edit.
  `settings.tabMarkers.mapKey.help` used to carry the "one key on its own" rule
  and no longer does: the recorder toasts it
  (`settings.tabMarkers.mapKey.error.withModifier`), so the help line is one
  sentence.
- `faq.screenshots.a` states two cadences and they come from the code, not
  from the prose: `GAME_INTERVAL` 700 ms and `IDLE_INTERVAL` 2000 ms in
  `src/shared/detector-rules.js`, and an idle tick **captures nothing** — it is
  one `Window.all()` enumeration looking for the game window
  (`MapDetector.tick()`). The `hotkeysGameOnly` poll in `core/foreground.js`
  reads, per window, the application name, the title, the size, whether it is
  minimised, the pid and whether it has focus — it is *not* "a list of window
  names", and it is not a capture. Re-read both files before touching that
  paragraph.
- **"points", one word per language, for what the code calls markers.** A
   deliberate simplification of the 1.0 rewrite: `markers.chip.*`,
   `settings.markers.hidden`, `settings.showPoints`, `settings.markers.opacity`,
   `settings.trouble.noPoints`, `settings.trouble.flash`,
   `settings.tabMarkers.instant*`, `settings.tabMarkers.method.*`,
   `tabMarkers.fallback`, `settings.where.*.help`,
   `settings.autoDetect.lockedHelp`, `home.autoDetect.locked`,
   `home.fullscreenNotice`, `hotkeys.action.toggle-markers`,
   `toast.markersOn` / `toast.markersOff`, `onboarding.layers.*` and
   `onboarding.recap.*` all use it, and so do the four FAQ answers.
   `markers.layer.*` — the full "… — possible location" the legend and the map
   draw — keeps the *marker* wording, because that is the one place the modal
   claim has to be spelled out. Do not mix the two words inside one screen.
 - `settings.opacity` / `settings.markers.opacity` are **"Visibility"** and
   **"Visibility of the points"**, not "transparency" and not "opacity". The
   approved mockup wrote *Trasparenza 80 %* over a slider where a higher number
   means *more* opaque, which reads backwards; the Italian
   (*Quanto si vede* / *Quanto si vedono i punti*) was already the honest form,
   so every language says how much you see rather than how much you do not.
   `toast.opacity` follows the label.
- `settings.whatToShow.help` / `onboarding.layers.body` — the app's single most
  misreadable claim ("the places where something **may** be, not where it is for
  sure"). Kept explicitly modal everywhere; the `<em>` sits on the word that
  carries it.
- `home.showing` is **"Map shown:"** — the label sits in front of the map's own
  name, so it has to be short and it may not say "overlay".
- `detector.detected` / `detectedAt` are **"Map recognised: {map}"**, so no
  language has to guess the gender or number of the noun `{map}` stands for.
  Only `src/js/detector.js` renders them, with `.text()`.
- `hotkeys.unbind` / `hotkeys.unbound` / `hotkeys.notBound` — English dropped
  "unbind" for **"Remove key" / "no key"**; the other languages had already
  chosen *desasignar / Sin asignar*, *entfernen / Nicht belegt*,
  *libérer / Non attribué*, *desvincular / Sem atalho* and should now match the
  plainer English. `hotkeys.deleteTitle` deletes a **key**, the same noun
  `hotkeys.deleted` reports.
- `settings.glideX` "Move it right" / `settings.glideY` "Move it down" and
  `settings.backToCorner` "Put it back in the corner" — all three say what the
  control does to the map, never "offset" or "snap".
- `faq.newMaps.a` "each map is downloaded **separately**" — the earlier "on its
  own" was read as "automatically" and mistranslated twice.
- `faq.updates.a` "works **even if** Check for updates automatically is off" —
  the earlier "works with the switch above off" was read as a precondition, and
  the sentence has no `<em>` to spare, so the label is quoted in plain text.
- `update.manual.portableBuild` "the releases page" — left as "releases", the
  GitHub page's own name.
